Arcane checks a permission, such as `containers:start`, on every action. A role is a named set of permissions. Users get every permission granted by their direct role assignments and by any [user groups](#user-groups) they belong to. There are no deny rules.

## Assign a role

<Tabs>
<TabItem label="UI">

1. Open **System → Users** and edit a user.
2. Under **Role assignments**, pick a role per agent.
3. Optional: narrow an agent assignment to a single resource (see [Scope roles to specific resources](#scope-roles-to-specific-resources)), or add a **Global** assignment for org-wide permissions.
4. Click **Save Changes**.

</TabItem>
<TabItem label="CLI and API">

The API uses `GET` and `PUT /api/users/{userId}/roles`.

```bash
arcane-cli admin roles assignments <user-id>
```

```bash
arcane-cli admin roles assign <user-id> --role role_deployer:<agent-id> --role role_viewer
```

`--role ""` clears every manual assignment.

</TabItem>
</Tabs>

Each assignment grants one role to a user or group at one of three scopes: **Global** (covering every agent and org-level endpoints), a single **Agent**, or a specific **Resource** on one agent. Org-level permissions like `users:*` and `settings:*` require a global assignment. You'll need to be a global admin to view or change assignments. Saving replaces a user's manual assignments, while assignments from [OIDC role mappings](/docs/access/sso) or LDAP sync are left untouched.

## Scope roles to specific resources

Instead of granting a role across an entire agent, you can narrow an agent-scoped assignment to a single resource. Resource-scoped assignments work on both users and groups, and Arcane forwards them to remote and edge agents so access is enforced consistently everywhere.

<Tabs>
<TabItem label="UI">

1. In a user or group's **Role assignments**, pick an agent and a role.
2. Change the scope dropdown from **All resources in environment** to a resource type (`Project`, `Container`, `Volume`, `Network`, `Image`, or `GitOps`).
3. For **Project**, pick the project from the dropdown. For other resource types, enter the resource identifier.
4. Click **Save Changes**.

</TabItem>
<TabItem label="API">

Include `environmentId`, `resourceType`, and `resourceId` on an assignment in `PUT /api/users/{userId}/roles` or `PUT /api/groups/{id}/roles`:

```json
{
  "assignments": [
    {
      "roleId": "role_deployer",
      "environmentId": "0",
      "resourceType": "project",
      "resourceId": "proj_123"
    }
  ]
}
```

All three fields (`environmentId`, `resourceType`, and `resourceId`) must be set together. Global assignments cannot be resource-scoped.

</TabItem>
</Tabs>

| Resource type | Identifier matched | Notes |
| --- | --- | --- |
| `project` | Project ID | Also covers the project's Compose-owned containers, volumes, and networks, images referenced by the project (for `images:list` and `images:read`), and GitOps syncs linked to the project. |
| `container` | Container ID or name | Applies to that container's actions, logs, stats, and exec. |
| `volume` | Volume name or ID | Applies to that volume, including workspace and backup routes. |
| `network` | Network ID or name | Applies to that network's read, connect, disconnect, and delete actions. |
| `image` | Image ID, repo tag, or repo digest | Applies to that image's read, tag, push, commit, patch, and delete actions. |
| `gitops` | GitOps sync ID | Applies to that GitOps sync configuration and sync actions. |

> [!NOTE]
> Collection-wide actions that don't target an existing resource — such as creating or pruning containers, projects, images, volumes, or networks — still require an agent-wide or global assignment.

## User groups

Groups let you manage role assignments for a team in one place instead of repeating them on every user. A user receives the union of their direct role assignments and the role assignments of every group they belong to.

Creating, editing, and deleting groups — as well as changing their members, role assignments, and IdP mappings — requires a global admin. Users with `groups:list` and `groups:read` can view groups in read-only mode.

<Tabs>
<TabItem label="UI">

1. Go to **System → Groups** and select **Create Group**.
2. Enter a **Name** and optional **Description**.
3. Under **Members**, select the users to add manually.
4. Under **Role Assignments**, add any global, per-agent, or resource-scoped role assignments for the group.
5. Click **Save**.

</TabItem>
<TabItem label="API">

Manage groups and their memberships with the Groups API:

- `GET /api/groups` and `POST /api/groups` — list or create groups (creation can include initial `memberUserIds` and `roleAssignments`).
- `GET /api/groups/{id}`, `PATCH /api/groups/{id}`, `DELETE /api/groups/{id}` — read, update, or delete a group.
- `GET /api/groups/{id}/members` and `PUT /api/groups/{id}/members` — list members or replace manual memberships.
- `GET /api/groups/{id}/roles` and `PUT /api/groups/{id}/roles` — list or replace the group's manual role assignments.

</TabItem>
</Tabs>

### Sync group membership from OIDC or LDAP

You can map OIDC or LDAP group claim values to an Arcane group so users are added to and removed from the group automatically when they sign in via OIDC or during LDAP sync.

<Tabs>
<TabItem label="UI">

1. Open an existing group under **System → Groups**.
2. Under **OIDC/LDAP Group Mappings**, enter the claim value from your identity provider (for example `platform-eng`).
3. Click **Add Mapping**. Repeat for any additional claim values that should map to this group.

</TabItem>
<TabItem label="API">

- `GET /api/groups/idp-mappings` — list mappings (optionally filter with `?groupId=<group-id>`).
- `POST /api/groups/idp-mappings` — create a mapping with `{"claimValue": "platform-eng", "groupId": "<group-id>"}`.
- `DELETE /api/groups/idp-mappings/{id}` — remove a manual mapping.

</TabItem>
</Tabs>

- Claim values are matched case-insensitively against the groups returned by your OIDC provider (configured via [Groups Claim](/docs/access/sso#map-provider-groups-to-roles)) or LDAP directory.
- Synced memberships are marked with an **IdP** badge in the member list. Manual memberships are never modified by OIDC or LDAP sync, and saving manual members leaves IdP-synced memberships intact.
- Deleting a group, removing members, or syncing from an IdP can never remove the last global admin; Arcane rejects or skips changes that would leave no global admin remaining.

## Create a custom role

You need to be a global admin to create, edit, or delete roles. Deleting a role removes every assignment of it.

<Tabs>
<TabItem label="UI">

1. Go to **System → Roles**.
2. Create a role, or clone a built-in one.
3. Pick its permissions and save.

</TabItem>
<TabItem label="CLI and API">

Pass one `-p` per permission:

```bash
arcane-cli admin roles create --name "Log reader" -p containers:list -p containers:read -p containers:logs
```

The API endpoint is `POST /api/roles`.

</TabItem>
</Tabs>

## Scope API keys

<Steps>

1. Go to **System → API Keys → Create API Key**.
2. Set a name, description, and optional expiration.
3. Under **Permissions**, pick the permissions the key holds. Keys created here get global grants.
4. Save and copy the value. It's shown once.

</Steps>

To scope a grant to one agent, use the CLI. Add `:<agent-id>` to the permission:

```bash
arcane-cli admin api-keys create ci-deployer -p projects:deploy:2 -p containers:list:2
```

The API equivalent is `POST /api/apikeys` with `environmentId` set on each grant.

A personal key from **Account → API keys → New key** carries no grants. It has the same permissions as your account.

Scoped keys carry their own global or per-agent permission grants, but a key can never exceed its owner's current access (checked on every request). You can't grant a key a permission you don't hold, and if an owner's role assignment is removed, their keys lose that access immediately.

## Built-in roles

You can't edit or delete built-in roles; they change only when you upgrade Arcane. To start from one, clone it as a custom role.

| **Editor**          | `role_editor`          | Full Docker, Podman, GitOps, webhook, job, vulnerability, and activity management, plus templates and variables. Read-only on users, roles, groups, API keys, federated credentials, settings, agent settings, registries, Git repositories, and S3 destinations. Can list, read, and sync agents, but not create, edit, delete, pair, or restart them. No Swarm init, join, leave, or unlock, no `system:upgrade`, no `gitops:lifecycle`. |
| **No-Shell Editor** | `role_no_shell_editor` | Editor without `containers:exec`.                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Deployer**        | `role_deployer`        | Everything Monitor has, plus read on registries, templates, and variables. Start, stop, restart, redeploy, kill, and pause containers. Deploy, stop, and restart projects. Pull, tag, and commit images. Check for **and apply** image updates. Container and Podman auto-update. Trigger GitOps syncs. Cancel activities. No create or delete, no settings, users, roles, or API keys.                                            |

## Global admin

A global admin is any user whose global assignments cover every permission, such as the built-in **Admin** role (`*`). System backup routes and authentication settings both require a global admin. Arcane always keeps at least one global admin, so removing the last one fails with `At least one user must retain a global Admin role assignment`. If nobody can sign in as an admin, see [Account Recovery](/docs/access/account-recovery).

## Permission catalog

`arcane-cli admin roles permissions` prints the catalog your server recognizes.

See [Permissions](/docs/reference/permissions) for every permission, what it requires, and the endpoints that check it.

### Special cases

| Permission             | Notes                                                                                                                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `notifications:*`      | Org-level. Needs a global assignment to manage **System → Notifications**.                                                                                                                                                           |
| `diagnostics:read`     | Covers runtime diagnostics and the live backend log. `diagnostics:profile` adds pprof profiles and goroutine dumps. Only Admin has them by default.                                                                                  |
| `gitops:lifecycle`     | Only in Admin by default. Allows configuring GitOps pre-deploy hooks, which run code from the repository in a container before deployment.                                                                                           |
| `gitops:backup`        | Gates **Back up to Git**. The shared sync routes need it in addition to the matching `gitops:*` permission when the sync is a backup.                                                                                                |
| `gitops:bidirectional` | Gates **Pull and push** syncs, the same way `gitops:backup` gates backups. Resolving a conflict also needs `gitops:sync`. Roles and API keys that had `gitops:backup` receive it on upgrade.                                         |
| `volumes:*`            | For [Volume Workspace](/docs/docker/volumes#volume-workspace) writes: `volumes:upload` allows creating and editing files, `volumes:delete` allows deletion, both allow moves and renames, and `volumes:backup` allows file restores. |
