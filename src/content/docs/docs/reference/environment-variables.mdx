This page lists the environment variables Arcane reads at startup. Most settings can also be changed in the Settings UI; use these when you configure Arcane from your Compose file or need a value in place before first start.

> [!IMPORTANT]
> Since 3.0, Arcane's own variables start with `ARCANE_`. `PUID`, `PGID`, `TZ`, `DOCKER_HOST`, `DOCKER_CONFIG`, the proxy variables, and `OTEL_*` keep their names. See [Migrate to 3.0](/docs/get-started/migrate-v3#environment-variables-are-renamed).

## Settings overrides

Set any setting below on the Arcane container to override it. The setting is then locked in the UI and shows **Set by** with the variable name. An invalid value stops Arcane at startup. Set `ARCANE_UI_CONFIGURATION_DISABLED=true` to make every setting read-only in the UI.

## Agent variables

An Arcane Agent needs three variables. Arcane fills them in for you in the install command it shows when you [add an environment](/docs/remote/environments#add-an-environment).

| Variable          | Value                                                                             |
| ----------------- | --------------------------------------------------------------------------------- |
| `ARCANE_EDGE_AGENT`      | `true` to run as an agent.                                                        |
| `ARCANE_MANAGER_API_URL` | The URL of your Arcane Manager.                                                   |
| `ARCANE_AGENT_TOKEN`     | The environment's API key. `ARCANE_AGENT_TOKEN_FILE` reads it from a file instead.       |

An agent stops at startup if `ARCANE_MANAGER_API_URL` or `ARCANE_AGENT_TOKEN` is missing. `AGENT_MODE` was removed in 3.0; setting it to `true` without `ARCANE_EDGE_AGENT=true` also stops startup. `ARCANE_EDGE_TRANSPORT` and the `ARCANE_EDGE_MTLS_*` variables are optional; see [Remote Environments](/docs/remote/environments#choose-a-transport) and [Edge Agent mTLS](/docs/security/edge-mtls).

## Container runtime user

When Arcane runs inside a container, it drops to the built-in non-root user (`65532:65532`) unless `PUID` and `PGID` are set. Arcane treats itself as containerized when `ARCANE_IN_CONTAINER=true` (set by the official images), when the `container` variable is non-empty, or when `/.dockerenv` or `/run/.containerenv` exists. Outside a container, the process keeps the user it was started as.

Set `PUID` and `PGID` if mounted files should belong to a specific host user and group. If you point `DOCKER_HOST` at a custom Unix socket, Arcane uses that socket path when it adds the runtime user to the socket's group.

## Timezone and scheduled jobs

Arcane's recurring jobs (image update checks, auto-updates, vulnerability scans, scheduled pruning, GitOps sync, and environment health checks) run on cron-style schedules evaluated in the timezone set by `TZ`. Set it to an [IANA timezone name](https://en.wikipedia.org/wiki/List_of_tz_database_time_zones) so jobs run at the local times you expect:

```bash
TZ=America/New_York
```

If `TZ` is unset, Arcane uses the container's local time, which is UTC on the official images. Job intervals and cron expressions are set in the Settings UI, or through [settings overrides](#settings-overrides).

## Admin API key bootstrap

Set `ARCANE_ADMIN_STATIC_API_KEY` when automation needs a known API key from the first start. At startup, Arcane creates or updates a protected admin API key with this value, so you don't have to create it in the UI. See the [API Reference](/docs/reference/api) for usage and webhook examples.

## Observability

Arcane exports metrics, traces, and logs when the standard `OTEL_*` exporter variables are set. See [OpenTelemetry](/docs/settings/opentelemetry) for setup.
